# Safari 接收器发布与回归规则

## 两次故障暴露的问题

1. Controller 的旧恢复标记优先于真实页面，导致已就绪的自提 Checkout 被退回 Bag 重建。
2. 页面里的 `__duoApplePayRequested` 历史标记被当成当前付款状态，阻止待机修复。人类报告也误把它称作“付款页面”。该标记只能证明脚本曾尝试请求，不能证明按钮点击成功、面板已出现或付款已完成。
3. 接收服务在线、浏览器连接成功，并不等于六个商品窗口在正确的自提状态。

必须分别核验流程行为、当前页面与运行服务。真实 Apple 页面测试和本地模拟互补，不能互相替代。

## 固定发布顺序

1. **本地回归**：运行下方全量命令；失败即停止发布。对每个生产事故补一个能在旧实现失败的回归用例，除了结果还断言导航/刷新次数和没有发生的错误操作。
2. **真实 Safari 预发布**：窗口行为相关改动，在隔离的 iPhone 18 测试窗口完成 1–3 轮测试。测试失败或窗口不存在就标记未验证，不宣称已通过；普通发布等待补测。紧急修复可以先部署，但必须明确记录跳过的检查、理由、影响范围和回滚版本。
3. **检查生产任务**：不能在正在处理库存、用户填资料或付款时重启。检查接收器 health 中 active_event_ids、recent_waiting、payment_panel_owner，并核对页面。一个来源为空不代表其他来源也为空。
4. **部署同一份代码**：保留上个运行版本，不用测试后又改过的代码直接上线。依赖/配置变化也要记录；回归报告中的核心源码哈希用于定位实际测过的版本。
5. **部署后只读核验**：服务 health、六个窗口实际待机状态、07094、产品匹配，以及运行目录源码哈希全部核对。不能仅看 ready 或进程存在。
6. **观察首次真实事件**：核对收到事件 → 首次刷新 → 门店 → 时间 → 联系人这些时间戳。保护用户正在操作的窗口。异常先定位证据，必要时回滚；不要用额外库存请求或连续刷新来探测生产。

本规则目前是人工发布要求及可执行检查入口，尚无强制部署流水线；绕过命令仍可能部署。后续可以把这些结果绑定到单一发布入口，阻止未通过的普通发布。

## 第一层：本地自动回归

从仓库根目录：

```sh
npm --prefix mac_receiver run test:release
```

重点矩阵：

| 场景 | 必须满足 |
|---|---|
| 正确自提页 + 旧 controller 恢复标记 | 新事件原页刷新一次；不去 Bag，不重新 Checkout |
| 十秒卡住、任务已终止 | 原 Checkout 恢复；旧协程不能继续点页面 |
| 全部门店不可选 | 只在已确认过期/结束的任务释放对应锁，不影响其他配置 |
| 回到无货 Fulfillment 的旧 Apple Pay 标记 | 空闲时原地清历史标记，恢复 ZIP；不伪报付款面板 |
| 有可选门店、联系人页或最后付款按钮 | 不按“无货待机”清除保护 |
| 页面未知、商品不符、session 弹窗、加载中 | 不冒认为就绪 |
| 重复/相邻请求及并行不同 SKU | 保持去重、10 秒候选有效期、同 SKU 互斥及各自超时边界 |
| 时间段 | 排除占位项，选择第二个可用项；下一步前验证日期和时间仍正确 |
| Session warning / expired | 精确续期或恢复到自提页；不以超时错误推断操作已经失败 |
| 实际到付款前 | 联系人读回与最后按钮就绪都需要证据，不能以中间标记替代 |

现有覆盖位于 `safari_standby.test.mjs`、`safari_adapter.test.mjs`、`safari.test.mjs`、`per_profile.test.mjs` 等；测试入口运行全部接收器测试，而不只运行新增的几个用例。

## 第二层：iPhone 18 真实 Safari 回归

入口：`mac_receiver/safari/regression.mjs`。复用 `prepareSafariStandby` 和 `prepareSafari`，没有另写一套选店/选时间算法。

前置条件：独立 `PickupTest18Pro` Safari profile，只有一个标签；购物袋为指定 iPhone 18 产品、数量一，已进入自提 Checkout。联系人放在未跟踪的私有配置文件。脚本不加购、不删商品、不修改生产配置、不操作生产窗口。

```sh
node mac_receiver/safari/regression.mjs \
  --config /absolute/path/to/private-test-config.json \
  --profile PickupTest18Pro \
  --url https://www.apple.com/shop/buy-iphone/iphone-18-pro/6.3-inch-display-256gb-burgundy-unlocked \
  --rounds 3
```

执行顺序：

- 从测试联系人页返回自提页，或复用当前自提页；设置/核对 07094，明确采用测试待机状态。
- **准备完成之后开始计时**。模拟新信号：刷新自提窗口 → 首个可用门店 → 第二个可用时间段 → 下一步 → 联系人填写和读回 → 最后 Apple Pay 按钮可见且工作流确认可用。
- 强制 `open_apple_pay_sheet:false`，即使私有配置写 true 也覆盖。拒绝测试期间 goto、add、checkout、requestApplePay。
- 不点最后付款按钮，不取消付款面板，不授权付款。每轮完整成功才进行下一轮，任一失败立即停止。完成后停在测试联系人页。
- 仅使用独立测试锁；发现残留锁先查对应 PID，确认没有另一轮运行再手动清理，不能自动抢锁。

报告输出到未跟踪的 `runtime/safari-regression/`，包含源码哈希、时间戳、操作序列、耗时及最终页面核验。只报告实际成功轮次；无货或服务错误算未完成，不算速度成绩。脚本总耗时还包括准备及回读，不应与计时段混用。

这个测试不覆盖真实库存事件的网络传输、iPhone Duo 的库存竞争、真实付款面板、指纹或订单成功。事件接收/路由/锁在本地并发测试中验证；必要时另做不影响生产窗口的隔离事件端到端测试。恢复、过期等角落状态优先本地确定性重放，不靠等待线上恰好发生。

## 第三层：部署后实际页面核验

下列命令仅通过 AppleScript 读取已指定的 Safari 窗口，不刷新、不导航、不点击：

```sh
node mac_receiver/safari/verify_standby.mjs \
  --config '/Users/trance/Library/Application Support/iPhoneDuo/receiver-safari/receiver.router.local.json' \
  --deployed-root '/Users/trance/Library/Application Support/iPhoneDuo/receiver-safari'
```

每个 profile 需商品匹配、自提模式、07094、待机 ready，并且没有 expired、session warning、abandoned 或保护状态；还对比核心源码和部署目录的哈希。非零退出码表示需要检查，**不授权清锁或改变页面**。如用户正在结账，等待完成后再验待机，不把真实结账页面强制恢复。

另外单独运行桥接 health，检查监听、活动任务、候选队列与 30 秒会话检查状态。只读页面检查是瞬时快照，不证明后台持续健康，也不证明将来的库存能抢到。

## 状态报告的证据要求

| 允许说的状态 | 所需证据 | 不能据此说什么 |
|---|---|---|
| 服务在线 | health 请求成功及监听状态 | 六个窗口已准备好 |
| 待机已核验 | 逐窗口真实页面、商品、自提、ZIP、保护状态 | 后续永不失效 |
| 最后付款按钮已就绪 | 联系人读回、最终按钮可见且可用 | 付款面板已出现 |
| 已请求 Apple Pay | 调用时间/回执 | 真实面板已出现或付款完成 |
| 历史付款请求标记存在 | 页面 marker | 当前在付款页 |
| 付款面板已确认 | 当时原生面板的直接观察 | 指纹已授权或订单成功 |

没有直接证据就写“未确认”，不得用保护原因猜测页面位置。本流程的真实回归主动停在最终按钮，因此固定报告 `payment_clicked:false`、`payment_sheet_verified:false`。

## 回滚与下一步

保留上个源码/配置快照及对应测试记录。回滚同样要避开活动任务，恢复后再验服务与实际页面；不能只报告重启成功。未来改进：单一发布入口自动强制全量测试、隔离 Safari 测试报告和版本哈希一致；为健康状态增加核验时间和页面阶段，让过期快照明确失效。长时间 Session 实测另开专用测试窗口，不增加生产刷新负担。
