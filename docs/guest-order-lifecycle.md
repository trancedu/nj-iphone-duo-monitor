# Guest 自动下单、恢复与诊断

## 当前策略

六个配置独立执行，每笔只有目标手机一台，含税总额最高 $3,000。额度不是设备终身总额；六个窗口每天共用四单上限，以 America/New_York 的自然日计算。测试模式不占用额度、不点击 Place Your Order。

同款只有一个工作流在操作页面。不同门店的同款通知也共享这个锁。处理中到达的同款通知只保留最新一条，原来的候选标记为 superseded；候选从发现/收到起超过10秒不补跑。第一条正常推进就继续，不被新通知打断；库存列表、时间或下一步卡住达到10秒时，可退出当前尚未提交的尝试，让最新同款从当前Pickup刷新重试。没有新鲜通知则等待，不构造无限重试任务。原流程最多两次额外库存刷新保持不变。

## 状态转换

| 状态/证据 | 自动动作 |
|---|---|
| 尚未点击下单，明确无货 | 释放同款锁，保留/恢复Pickup，等待新鲜通知 |
| 尚未点击下单，时间/下一步超时 | 安全终止旧工作流，从当前会话恢复Pickup；新鲜同款通知可以接替 |
| 预填付款信息丢失 | 重新走一次配送/付款准备，再回Pickup；失败则暂停该配置，其他配置继续 |
| 最终提交之前 | 持久化占用全局每日额度，再调用Place Your Order一次 |
| 明确付款失败/库存失效 | 额度记录标记failed，立即释放锁；当前Guest会话回Fulfillment后处理最新有效通知 |
| 明确成功，且目标商品和提交归属匹配 | 成功计数；立即释放锁，在同款窗口补购物车、预填配送/付款，再回Pickup/07094 |
| 点击后20秒仍无法确认结果 | 标记order_result_unknown，继续只读观察；不刷新或再次提交，保留额度和现场 |
| 成功后补购物车/预填失败 | 成功计数不撤回；该配置暂停，保留阶段和错误日志，其他配置继续 |
| 第四单已占用额度 | 拒绝新的提交需求，返回daily_order_limit_reached；下一美东自然日恢复，但历史未知结果仍占位 |

“收到点击返回”“窗口已关闭”“页面卡住”“购物车空了”都不单独证明支付失败或订单成功。20秒超时不等于未扣款。银行验证、验证码、3DS、验证码图片、站点升级、Keychain锁定等仍可能需要人工解决；不能承诺任何故障都能无人值守。

## 每日额度与重启

`order_ledger.mjs` 在router state_dir保存 `guest-order-ledger.json`。六个配置共用一个实例；写临时文件、fsync，再原子rename。占位发生在最终按钮调用前。已成功和未知记录不会因同款锁过期而删除。失败记录释放当天额度。

进程重启会导入历史提交证据；旧的未决订单继续保护，不会被普通60秒锁超时或一键清锁绕过。最终结果未知时，后续同款只等待/过期，其他未超额度的配置仍可执行。成功后的准备途中如果重启或失败，配置会保守暂停，防止不明状态下补入重复商品。

成功恢复只允许在确认成功之后向空购物车补加一台。购物车已有准确的一台就复用；存在其他商品、错误配置或多台则停止，绝不清空或盲目再添加。配送预填函数和PickupTest测试共用 `guest_setup.mjs`。允许的生产profile与商品必须一一对应。

## 会话与取证

普通检查每30秒读取已有页面状态，不代表每30秒刷新。出现继续购物提示则精确点击；已过期的Guest会话可用私有配送配置及Keychain重新准备，失败有3分钟退避。活跃订单与结果未知页面不参与空闲维护。初始化时会话检查时间与20分钟完整刷新错峰时间分开，避免后几个窗口首次检查被额外延后。HTTP接收先上线，准备工作在后台串行进行；每个正在准备的配置接到通知时只暂存最新候选，其他窗口不因启动准备失去接收服务。

`events.jsonl` 关联event_id，记录候选取代/过期、额度预留、提交、确认、解锁、补车和准备的时间。`diagnostics.jsonl`保留安全字段及页面阶段、门店状态、DOM/AppleEvent耗时；不保存卡片、联系人或HTML。`session-watch.jsonl`记录会话检查，`evidence.jsonl`记录截图成功/跳过原因。

可选 `failure_screenshots=true` 使用本机window-id helper定位唯一Safari窗口。不弹权限申请；无屏幕权限时直接跳过。截图仅允许Pickup或过期页，排除联系人/Billing/Review，页面变化或新事件启动则丢弃；子进程限时、异步执行，不占用下单步骤。每配置最多五张，目录0700，图片0600。用户仍可能在取证瞬间操作页面，因此图片按私人诊断资料管理。一般无货不截图。

## 验证及实际边界

自动化测试覆盖配额并发、四单上限、失败返还额度、跨日、未知结果/重启、同款候选合并、Guest短状态名、准备函数隔离及最终按钮保护。实机只在PickupTest18Pro运行共用准备函数和测试下单流程，停在Review，未创建真实订单。

成功后实际Apple确认页的布局目前没有真实订单样本；识别要求可信Apple主机、明确成功标题、匹配商品和持久提交归属。布局不满足时会保留未知结果，不能将这部分称为已经实单验证。缺少时段、商品消失、403/503等只记录事实，不将其统一归因于风控。

## 后续可提高成功率的方向（尚未全部实现）

1. 用真实成功订单的脱敏确认页完善成功识别，并建立确认页、缺时间、付款失败、503、session过期、Keychain拒绝的固定HTML回归样本。无需为收集样本额外下单。
2. 分别统计通知传输、排队、刷新到库存、时间窗口返回、联系人和Review的p50/p95；只优化占比最大的阶段。当前同步DOM计时不能精确代表网络或异步渲染。
3. 为明确的发卡行拒绝增加跨配置熔断，避免错误卡信息被多个窗口反复尝试；为503/429增加带上限的全站退避。未知订单先核实，再考虑恢复。
4. 将长会话重建与轻量状态检查拆开调度，避免一个窗口重建期间其他窗口的检查被延迟；保持真实库存事件优先。当前一次长维护仍可能推迟其他空闲检查。
5. 从日内成功数扩展到用户明确设定的商品/金额/门店限制和重复订单提示；不自动取消已成功订单。
6. 在尽量不增加Apple请求量的前提下减少重复读DOM、复用已校验字段。多IP轮换并不能解决时间窗口/库存竞争，也不保证规避限制，应先用日志证明瓶颈。
