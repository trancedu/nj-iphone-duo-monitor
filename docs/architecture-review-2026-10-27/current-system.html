当前系统：架构、链路与代码审阅

从 Mini 的一次库存查询，到 Mac 四个 Safari Profile 的人工付款交接：当前实现、实际证据、边界与需要整理的地方。

核对时间：2026-10-27 00:11 EDT · 中文工程文档 · 源码提交 8d24561 · 本轮仅新增两份 HTML，不修改程序、不重启服务、不发购物/付款请求

CHAPTER 01

Big picture：它已经是一个小型分布式系统

系统的目标是把“看到可自提库存”尽快转成“正确商品、正确门店、正确联系人已经准备好，用户接手付款”。它分为检测平面、事件传输平面、浏览器执行平面、通知与运维平面。运行时没有 AI 模型参与判断或点击：Python、Node.js、AppleScript 和 DOM 规则确定性地执行。

检测
Mini / Python

代理出口池查询库存；解析四款 SKU 和门店日期，产生确认的库存观察。

执行
Mac / Safari

按商品 URL 分派到四个 Profile，校验购物袋，准备门店、时段和联系人。

最终动作
用户付款

现有代码没有最终 Apple Pay 操作；到按钮之前停下，保留页面与任务锁。

本轮确认到哪里？已读取仓库源码和本机认证 health：Safari live、四个 Profile 可读、无 active / held。没有登录 Mini 检查其现时监控进程、有效出口数、桥接开关或 Telegram 送达；这些不能由 Mac health 推断。

阅读顺序：先看总图与模块，再看一次事件如何流动，最后看代码整理与运维缺口。配套 roadmap 讨论未来改变，不应把未来建议当成当前功能。

CHAPTER 03

模块怎么连接：总图与责任

01 / MINI调度器 → Mihomo

proxy_monitor.py 按全局节奏、每出口冷却与并发上限选择一次库存请求。

02 / APPLE库存响应 → 解析器

monitor.Client 请求 pickup-message；regional_payloads / parse_inventory 验证门店、SKU、可选性和日期。

03 / MINI确认观察 → 两条独立通道

notify_offer 先记录/提交LAN队列，再处理Telegram到货去重与发送。

04 / LANSQLite outbox → Mac HTTP

Mini主动POST /prepare；后续主动GET /status。没有Mac回调Mini、没有WebSocket。

05 / MACProfileRouter → Engine

认证与来源检查后按URL路由；每Profile独立去重、active锁、held队列与状态文件。

06 / SAFARIAppleScript → DOM → 用户

固定Profile窗口检查购物袋和自提步骤；异步语音/通知，最终付款留给用户。

主数据流：Apple库存 → Mini观察事件 → LAN HTTP → Mac状态机 → Safari页面。通知支线：Mini → Telegram → 手机/手表；Mac → 本地系统通知/声音。GitHub只同步源码，既不是消息队列，也不控制浏览器。

CHAPTER 04

检测层：四款一次查询，响应质量比次数重要

生产代理入口按文档和部署参数使用ZIP 07094，默认要求该区域已知12店完整；每个请求同时携带四款SKU。配置文件还保留旧两区域07078/11530与22店目录，但那不代表当前代理进程自动查询这两区。SKU/URL是本仓库当前映射，本轮没有重新发现Apple商品目录。

有效库存必须同时满足：响应包含预期数据；门店可选择；pickupDisplay为available且不存在unavailable文案；日期可解析且编码/文案没有冲突；取货上界在美东今天至未来3天。配送日期不触发。缺SKU、缺门店、错区域、未知结构是查询错误，不能归为“无货”。

APPLE_PICKUP_ZIP在进程启动加载后替换旧区域，启用动态返回门店验证；不是在原两区上再加一个ZIP。Mac优先级是其环境覆盖 > 事件ZIP > 配置fallback。这一设计允许切区，但也可能让检测区域与checkout区域不一致；未来应明确记录effective_zip与覆盖来源。

跨州切ZIP还没有完整解决时区：pickup_details.mjs的时段计算固定使用America/New_York，库存日期也以美东当天判断。切到California不等于门店当地日期/时段语义正确；后续需把store_timezone作为明确数据贯穿解析和checkout。

CHAPTER 05

代理层：调度、冷却和已有性能证据

启动时读取本地Clash remote订阅缓存，排除非真实节点项，启动独立Mihomo环境。每候选节点做非Apple出口探测，再按测得IPv4去重。名字不同、订阅不同不等于出口不同；同一出口共享冷却。只启动时测量，运行中是否换出口、Apple看到是否同IP未得到保证。

参数 / 行为当前代码或部署值含义
节点上限256；部署使用all-subscriptions是候选配置上限；不是健康出口数或Apple成功出口数。
启动间隔至少2秒全局最多约0.5次/秒发起；不是每2秒成功。
在途请求部署workers=4；CLI允许1–8慢请求可重叠；状态更新与通知仍在主线程。
同测得出口间隔至少60秒且不同时在途重启保留last_started与blocked_until。
403 / 429 / 541默认5、10、20、40、60分钟退避541原因没有被证明；不能直接叫作按IP限流。
429 / Retry-After阻止后续全局派发；已在途可完成换出口不会绕过全局退避。
网络错误从60秒开始延长冷却不是无货，也不是直接重试。
历史数字该怎样读

10/25十分钟实验：150次查询，89次有效响应、39次541、22次网络错误，平均每分钟8.9次成功。10/26两订阅两分钟实验：60次请求，30次有效、26次541、4次网络错误，成功完成最大间隔21.067秒。这两轮使用旧“白256固定+随机另一款”策略；当前四SKU策略与长时间生产质量不能由这些短实验推断。

判断监控质量应看成功完成间隔的P50/P95/P99、各SKU×门店观察年龄、连续空窗、错误率和出口健康，而不是只看queries或HTTP200。

CHAPTER 06

事件传输：一次信号如何可靠地到 Mac

  1. notify_offer写可用观察，并调用LAN hook。桥接需环境PICKUP_MAC_CONFIG及配置enabled=true；本轮未核验Mini开关。
  2. Bridge.submit把offer放进128容量内存Queue，立即返回；后台tick每轮最多转存32项到SQLite。只有转存成功后，事件才可跨重启恢复。
  3. 按门店+SKU+取货日期计算dedup键；1800秒内复用最初event_id和payload。POST回执丢失时仍用原ID重试，避免再次启动浏览器。
  4. 默认请求超时1秒、POST最多3次，延迟0.5/1秒；该超时含接收端窗口探测与HTTP响应等待，不能保证每次来得及。
  5. queued/held/running后约5秒查一次status；观察期限是Mini持久化起180秒。超时停止观察，不取消Mac任务。
  6. Telegram到货消息独立走原去重/发送；Mac离线不能阻止到货通知。桥接故障通知另有全局10分钟冷却。
当前语义是“至少一次尝试 + 去重”，不是整个交易exactly-once内存到SQLite有丢失窗口；事件去重避免同ID重复执行；购物网站或支付订单的不可逆副作用没有exactly-once保证。未来支付层必须单独建立订单核对机制。

注意30分钟去重的副作用：同SKU/店/日期第一次无货、失败或刚恢复后再次有货，仍可能映射原事件，不会再触发一轮。它是“提醒去抖”规则，未表达新的库存机会。后续应分离observation_id、attempt_id和purchase_intent_id。

CHAPTER 07

LAN 协议：认证、接口和信任边界

接口权限 / 行为关键返回
GET /health来源许可+Bearer；含Profile和音频队列状态200不代表付款准备完成。
POST /prepare同样认证；JSON≤8192字节；ID/URL/时间戳校验202 queued/held；同内容重复200；409冲突/busy；429容量；503未就绪。
GET /status/<event_id>读取Mac阶段/结果，必要时触发held过期处理200状态或404；Mac不会主动callback。
POST /reset仅回环来源+confirm=true；运行中拒绝Safari先恢复正确袋再释放锁；不是取消支付接口。

接收端按socket实际来源IP检查，不信任X-Forwarded-For；拒绝浏览器Origin；Bearer比较使用定长摘要及恒定时间比较。商品URL限定Apple HTTPS规定路径，不接收Cookie、联系人或卡号作为事件字段。固定URL映射使未知商品不能随意启动Profile。

当前服务是http.createServer，Bearer在可信LAN以明文HTTP传输。私网IP白名单不能代替加密；若跨不可信Wi‑Fi或异地部署，应另做加密通道与身份生命周期。当前不应公网映射。

CHAPTER 08

执行层：四个 Profile 和任务状态机

新事件 → queued → running ─┬→ awaiting_user → 人工付款/释放
                          ├→ pickup_unavailable → 恢复袋成功 → 释放
                          └→ manual_review / interrupted → 保留锁
同Profile忙/窗口未就绪 → held → 空闲且未过期 → queued
                                  └→ expired
重启：queued/running → interrupted；held → expired

四个Profile各自有active锁、历史、held队列；商品URL决定路由。同一Profile最多一个执行任务，其他事件可held。四路可以独立进行，但共享一个Node事件循环、Safari和AppleScript，不能当成四台独立机器或保证四倍速度。

当前每Profile历史上限4096项，达到后拒绝新事件；重置只释放active，不删除历史。状态文件全量同步写入并原子rename，阶段越多、历史越大越可能增加主进程I/O。JSON原子替换有助避免半文件，但不是完整数据库事务、fsync持久保证或自动归档。

存在两个时间问题：held按detected_at限制TTL；新入站queued只验证时间戳格式，不检查太旧/未来时间。Mini正常sender有180秒约束，但手动或其他合法来源仍可能提交陈旧新事件。未来接收端要独立验证新鲜度。

CHAPTER 09

Safari 流程：哪些步骤已经自动化

  1. 绑定窗口：从Safari窗口名精确识别Profile，要求唯一窗口且单tab，再固定window ID。缺失、重名、多标签会停止；不会任意接管日常窗口。
  2. 校验袋：恰好目标商品1台则复用；空袋才进入商品页，选择No AppleCare并Add一次，再Review Bag核验。未知商品、多件、数量异常停止。Safari生产路径不自动清空其他商品。
  3. 进自提：点击购物袋的Checkout with Apple Pay，选择I’ll pick it up，必要时填ZIP；此处是checkout导航，不等于钱包授权。
  4. 核验门店：优先事件store_name，必要时展开更多门店。store_id目前主要进入诊断，实际选择依赖门店名；目标缺失、不可选、未知结构是不同结果。
  5. 有限刷新：目标明确不可选时最多10次额外刷新，刷新前再查一次；有货就停止刷新。不是后台无限刷新。
  6. 继续准备：选门店、可用日期和配置偏好的时段，Continue to Pickup Details，填已配置联系人并读回验证。
  7. 交接：验证最终Continue with Apple Pay可见/可用，置前、语音/通知，停下。DOM派发器没有最终支付操作。

另一个日期边界：Mini的offer包含取货date，但Bridge事件没有携带该date；Safari会重新选择页面默认/可用日期，时段逻辑可接受未来7天。因此“库存过滤今天至3天”不是接手页面也严格同一天/3天内的端到端保证；需要把日期窗贯穿事件与页面复核。尚无证据表明已经发生错日。

本地测试使用Playwright/Chrome夹具验证流程；真正Safari由AppleScript向页面执行DOM函数。Chrome后端、五页预热、四Profile隔离实验保留在仓库，但不是当前Safari主入口。

CHAPTER 10

无货恢复、人工接手和闲置策略

若仍无货，系统可响提示后恢复预置正确袋，成功才释放锁；恢复失败保留锁。若曾发现可用库存或已进入门店/时段/联系人阶段，后续误报无货转manual_review，保护页面。成功awaiting_user通常保持锁，同Profile后续事件等待。

当前health报告600秒交接闲置阈值、300秒待命袋刷新。交接页真实用户活动重置闲置计时；付款开始、页面变化或不可判定时保留锁。闲置返回须原子确认、回袋并校验后才释放。待命袋刷新要求无active/releasing/signaling、无接收预约、未聚焦、确实目标一台且在bag页。

Safari每2秒的元数据轮询用于窗口/队列检查，不是每2秒刷新购物袋。关闭单个任务窗口后需要同Profile重新打开才能恢复；退出整个Safari不自动解除全部任务锁。重启router时四个Profile逐一start，任一路窗口异常可使整个服务启动失败；运行中暂缺一路的held恢复与启动容错是两回事。

CHAPTER 11

声音、Telegram、手表：三个不同成功条件

收到库存事件开始执行时播简短配置语音，例如“五一二白”，并不代表checkout已核实有货。最终ready保留文字通知，可跳过重复语音。声音通过全进程FIFO队列后台播放；32个待播上限，队列/播放器失败不应卡住购物流程。

代码调用afplay/say，不会在运行时取消系统静音或改系统音量。历史曾手动将音量设为70%；那不是每次提醒都会发生。Mac静音不会阻止LAN执行或文字通知。

Mac本地display notification没有直接手表推送实现。手表取决于手机端应用通知/Watch镜像/佩戴解锁及专注模式。Apple说明，iPhone解锁时通常通知在手机；锁屏或休眠时通常到未锁定手表。[官方：Watch通知]

记录字段实际证明没有证明
audio_queued=true音频任务已进入本地队列人听到了；电脑未静音。
sound_played / speech_spoken播放子进程报告成功输出设备正确、用户醒来。
notification_submitted=true系统接受通知脚本调用横幅可见、手机/手表收到。
Telegram API成功服务端接受消息手表振动、用户确认。
awaiting_user浏览器准备流程完成付款已授权、订单已成立。
CHAPTER 12

运行与部署：当前最容易混淆的地方

本机生产LaunchAgent是com.trancedu.apple-pickup-router，运行目录是~/Library/Application Support/iPhoneDuo/receiver-safari，入口profile_router.mjs。当前仓库里的deploy/mac_receiver_service.py却仍安装旧label apple-pickup-receiver与server.mjs单入口。因此它不能被描述为“从零重建当前四Profile Safari生产”的安装器。

另一个漂移点是watchdog.py只看旧monitor job与旧runtime/state.json。它没有覆盖代理current.json、Mac router、Safari窗口、LAN投递、手表通知。当前四路health可用，也不等于有独立外部watchdog。

未来应将“git源码版本”“Library bundle版本”“正在运行版本”“配置版本/迁移版本”各自暴露，并提供可回滚安装流程。更新文件前先检查active/held；有人工付款交接时不要按通用部署脚本强行重启。

适合日常排查的只读命令
git status --short --branch
git log -1 --oneline
launchctl print gui/$(id -u)/com.trancedu.apple-pickup-router
python3 bridge_client.py health   --env-file "$HOME/Library/Application Support/iPhoneDuo/receiver-safari/.env"   --endpoint http://127.0.0.1:8765
# Mini端由实际部署用户查看：
# runtime/proxy-monitor/current.json
# runtime/proxy-monitor/pickup-bridge/delivery.jsonl

不输出.env，不把完整私密配置、订阅URL、Cookie、联系人或支付页截图放入共享报告。

CHAPTER 15

验收与故障排查：用什么证明“好用”

现象先检查正确结论 / 后续动作
没有库存消息Mini进程、last_success年龄、解析错误、覆盖无消息可能是无货、无数据或通知失败；不能只看进程存在。
Telegram有消息但Mac没动桥接enabled、outbox phase、delivery、LAN权限相同event_id查status；避免生成新ID导致重复任务。
health=ok但无法接手对应slot窗口、cart、阶段reason、配置版本ready不是钱包就绪；不要反复reset覆盖页面。
一直held该Profile active锁、检测时间、TTL、窗口held过期正常；reset要先确认用户已完成/放弃。
声音没听见系统静音/输出设备、audio_queue、feedback播放成功不等于人收到；手机/手表另做受控通知验收。
升级后仍旧行为源码hash、bundle hash、进程启动时间git pull不会更新运行进程；先保护active再部署。

本轮仅做只读源码/health审阅与文档检查，没有重新跑库存查询、没有触发Safari购物、没有付款，也没有把前一轮测试结果冒充本轮全套测试。未来建议验收采用：离线parser与DOM fixtures → 本地HTTP契约与故障注入 → 专用Profile人工commissioning → 小窗口生产观察。
